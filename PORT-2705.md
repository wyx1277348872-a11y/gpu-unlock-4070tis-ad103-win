# RTX 4070 Ti SUPER (AD103, `10de:2705`) — Windows preboot port

This tree is a fork of [Zihao-Wu06/gpu-unlock-for-windows](https://github.com/Zihao-Wu06/gpu-unlock-for-windows),
which is itself a Windows UEFI port of [Zagitta/gpu-unlock](https://github.com/Zagitta/gpu-unlock) and
[JustAResearcher/gpu-unlock-ada](https://github.com/JustAResearcher/gpu-unlock-ada).

Upstream targets one card: **RTX 4090, `10de:2684`, AD102, 24 GB**. This fork adds a reviewed
profile for **RTX 4070 Ti SUPER, `10de:2705`, AD103, 16 GB** and the one topology fix that card
needs. The firmware transaction, payload and every gate are otherwise unchanged.

> **Status: one machine, one card, four cold boots.** The result below was measured on a single
> MSI RTX 4070 Ti SUPER. It is not a claim of support for other AD103 boards, other 4070 Ti SUPER
> VBIOSes, or long-term stability. Treat this as a worked example, not a supported product.

## What was measured

Same machine, same driver (616.56), same 330 W power limit, cuBLAS 8192³ GEMM, best of 25 runs
after 8 warmups:

| Path | Stock | Unlocked | Ratio |
|---|---:|---:|---:|
| FP32 (CUDA cores, control) | 29.70 TFLOPS | 29.42 TFLOPS | **0.99×** |
| FP16 → FP32 accumulate | 84.92 TFLOPS | 149.67 TFLOPS | **1.76×** |
| FP16 → FP16 accumulate (control) | 85.96 TFLOPS | 149.08 TFLOPS | 1.73× |

The two controls are the point. FP32 scalar does not move, and after the unlock the FP32-accumulate
path reaches the same rate as the FP16-accumulate path — which was never throttled. That is what
"restored issue rate" looks like. The GEMM ratio is below the 2× the instruction-level probes report
because cuBLAS is also bound by memory bandwidth and scheduling.

Selector readback from the transaction log, on the same boot:

```
SELECTOR RESULT: SS0 before=0 after=0x88888888 expected=0x88888888 matched=1
SELECTOR RESULT: SS1 before=0 after=0x8 expected=0x8 matched=1
POST-FLR SS0=0x88888888 SS1=0x00000008
POST-GOP SS0=0x88888888 SS1=0x00000008
FINAL status=0 stage=post-unlock-handoff attempted=1 driver_release=1 clean=1
```

`SS0`/`SS1` survive the PCIe FLR and the GOP reconnect. No `NVRM Xid` events, `nvidia-smi` healthy,
both attached monitors came back.

## What actually changed

Three files, ~90 lines. Nothing in `vendor/` — the AD102 four-PLM payload path was already present
upstream and is used as-is.

### 1. `efi/windows/uefi/ownership.c` — a child controller with no GOP

This board's firmware binds **two** child controllers to the target GPU. One exposes a Graphics
Output Protocol and drives the console; the other exposes **no GOP at all**, even with a monitor on
that connector. Upstream's `DisplayChild()` required every child to be a valid GOP display and
returned `EFI_UNSUPPORTED` for the second one, which made `GuFindReleaseOwner()` fail, which aborted
the run at `stage=ownership` before any GPU write.

A child with no GOP cannot present a UEFI console, so it is not a display resource the transaction
has to restore. The fix counts it as a non-display child and continues:

```c
if (EFI_ERROR(status) || !gop || !gop->Mode) {
    Owner->gopless_children++;
    GuLog("display child without GOP: handle=%#llx counted_as_non_display=1\n", ...);
    return EFI_SUCCESS;
}
```

This does **not** remove the display guarantee. `DisplayCheck()` still requires exactly one physical
framebuffer GOP on the target before and after the handoff, so a card with no display output is
still refused. `gopless_children` is added to `GuSameReleaseOwner()`, so the arming snapshot still
pins the count: plugging or unplugging a monitor between the two snapshots aborts the run.

### 2. `efi/windows/build.py` — board identity

The unlock build's gate was hardcoded to `0x268410DE` / `0x192000A1` / 24 GB. It is now selected by
`GU_LOCAL_BOARD`, and `GU_TARGET_PCI_ID` is derived from the captured profile instead of the RTX 4090
default. **Unset, the original 4090 gate is unchanged.**

Every other gate is untouched: `class/rev`, PCI command, header type, ROM enable bit, `wpr2_hi`,
`ss0 & 0x88888888`, `ss1 & ~7`, BAR consistency. They all passed on this card as-is, so there was no
reason to weaken them.

### 3. `efi/windows/uefi/probe.c` — read-only enrolment

The probe's own identity check now reads `GU_BOARD_ID`/`GU_BOARD_CHIP` from the profile header, and a
chip mismatch is recorded (`chip_matches_profile=`) instead of aborting, so a first capture completes
even if an assumption is wrong. The unlock build does not include this path.

## Captured constants for this card

From two independent cold captures. Every value below is what the firmware reported, not an
assumption:

| Field | Value |
|---|---|
| PCI | `0000:01:00.0` |
| `vendor:device` | `10de:2705` |
| Subsystem | `6688:2705` |
| Class/rev | `030000a1` |
| Chip | `0x193000a1` |
| VRAM | 16 376 MiB (`0x3ff8`) |
| BAR0 | `0xde000000`, 16 MiB, granularity 32 |
| Cold `WPR2_HI` | `0` |
| Cold `SS0` | `0x30463023` (two boots: `0x30463023`, `0x30263163` — see note) |
| Cold `SS1` | `6` |
| FWSEC | `engine=0x400`, `ucode=9`, `sigs=2`, `versions=3`, `imem=0xf700`, `dmem=0xd80` |
| PCIe cap | PM `0x60`, MSI `0x68`, PCIe `0x78`, no MSI-X |

**Note on `SS0`.** It is not constant across cold boots — two captures gave `0x30463023` and
`0x30263163`, differing in bits `0x00400000` and `0x00004000`. That is why the gate tests
`ss0 & 0x88888888 == 0` (the "already unlocked" bits) rather than equality with a recorded value.
Do not pin the full word.

## Known limitations

- **One card, one board.** Another 4070 Ti SUPER with a different VBIOS will very likely fail the
  PROM or chip gate. That is the intended behaviour; run the read-only probe and build your own
  profile rather than editing constants until it passes.
- **`FBPA` does not reach its requested value** (`0xffffff0f` vs `0xffffffff`). The code treats it as
  non-fatal and the Linux canary report for this same card records the same behaviour. The three
  required permissions (`WPR_CFG`, `WPR`, `FEAT`) do reach their targets.
- **The unlock lasts one boot.** Power off and it is gone; the selectors reset. Every cold start must
  redo the transaction.
- **No benefit for mining or INT8.** This restores the FP32-accumulate tensor issue rate only.
  Ethash/KawPow/PearlHash-style workloads and quantised integer inference run on paths that were
  never throttled.
- **Suspend/resume is untested** and expected to lose the unlock.

## Build

Requires Windows x64, Python 3, and **Zig 0.15.2** (`zig cc` for `x86_64-uefi`). No MSVC needed for
the EFI itself.

```sh
# read-only probe first: never writes GPU state
python efi/windows/build.py probe --zig <zig-0.15.2> --output build/probe

# unlock image, bound to a probe run directory
set GU_LOCAL_BOARD=2705
python efi/windows/build.py unlock --zig <zig-0.15.2> --run <GPU-UNLOCK/RUNxx> --output build/unlock
```

`unlock` without `-DGU_AUTO` (see `efi/windows/build_manual.py`) keeps the manual path: the program
prints READY and waits for an explicit `U`, and stops on refusal instead of continuing. The upstream
`build.py` adds `-DGU_AUTO`, which starts the transaction at every boot with no prompt — convenient
once a board is trusted, risky for a first attempt.

Build output embeds source paths through `__FILE__` in the diagnostic macros. Build from a path you
are willing to publish, or strip them, before distributing a binary.

## Firmware assets

Not included, and must not be redistributed. Generate them locally from hash-pinned NVIDIA inputs:

```sh
git clone https://github.com/Zagitta/gpu-unlock.git
cd gpu-unlock && git checkout --detach 0ebdb1c6308b6a2072be5bf04513472942541956
make inputs firmware INPUTS="$PWD/inputs" ASSETS="$PWD/assets"
```

Copy these five into `GPU-UNLOCK/ASSETS/` on the boot volume. `efi/windows/uefi/assets.json` pins
their sizes and SHA-256.

```
booter_load_ad102.bin                    57,672
v67-ad102-610.43.03-four-plm.bin         64,000
gsp_ga10x.bin                        84,277,400
gsp_boot_ad102.bin                       36,864
gsp_boot_desc_ad102.bin                      84
```

## Rollback

Nothing is flashed. Power off, boot `Windows Boot Manager`, and the card is back to stock. Delete
the boot entry and the dedicated FAT32 partition to remove the tool entirely.
